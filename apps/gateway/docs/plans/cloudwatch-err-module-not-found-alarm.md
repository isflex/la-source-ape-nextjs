# Plan: CloudWatch alarm on `ERR_MODULE_NOT_FOUND`

> **Status:** nice-to-have, future implementation. Captured 2026-05-14 as the standing
> follow-up from the `posthog-node` 500 fix (see `next.config.mjs:152-160` for the
> shipped workaround). Not yet scheduled.

## Context

The `posthog-node` 500 (already fixed in a separate change) reached real users because there was no signal between *the SSR Lambda failed at module-load time* and *we noticed*. The class of error — a missing externalized package — surfaces only as `ERR_MODULE_NOT_FOUND` in the Lambda's `console.error` output, *before* any user code (try/catch in `server-error-logger.ts`, the Next.js `instrumentation.onRequestError` hook, PostHog capture, the custom CloudWatch writes) gets a chance to run. So the failure currently lands in the Amplify-managed SSR Lambda log group with no downstream routing.

Goal: deploy a CloudWatch metric filter + alarm + SNS notification that fires within ~1 minute of the *next* time any externalized package goes missing in the SSR Lambda, regardless of which route triggers it.

## What this is NOT

- Not a generic "all server errors" alarm — those already flow into the custom `/apelasource/gateway/errors` group via `server-error-logger.ts:240-275` and PostHog. Module-resolution failures bypass that path entirely; this alarm targets specifically that bypass.
- Not infrastructure-as-code for Amplify Hosting itself. The SSR Lambda + its log group are owned by Amplify Hosting; we reference the log group by name, we don't manage its lifecycle.

## Mapped current state

Confirmed via exploration of this repo:

- Amplify Gen 2 backend at `apps/gateway/amplify/backend.ts:1-47`. Existing pattern uses `defineBackend({...})` + `backend.createStack('<name>')` to attach custom CDK constructs (e.g. the S3 bucket reference at lines 20-32). No alarms, metric filters, or SNS topics defined anywhere.
- Commented-out CDK block at `apps/gateway/amplify/backend.ts:49-63` would create the user-owned `/apelasource/gateway/errors` log group. Worth uncommenting as part of this plan so the log group's lifecycle is in IaC rather than implicit.
- Error logging code path: `apps/gateway/src/lib/server-error-logger.ts:205-275` writes to `/apelasource/gateway/errors` via `@aws-sdk/client-cloudwatch-logs`. **Does not capture** the `ERR_MODULE_NOT_FOUND` class because that throws before this code is loaded.
- Region: `eu-west-3` (fixed in `env/public/.env.production`, fallback in `secrets.ts:7` and `server-error-logger.ts:199`).
- Notification channels in use today: **none**. Errors flow to CloudWatch + PostHog, neither is wired to alert humans.
- The user's email is `hello@flexiness.com` — sensible default for the SNS subscription.

## Design

Add a small CDK stack inside the existing Amplify Gen 2 backend that:

1. Creates an SNS topic (`flex-gateway-alerts`).
2. Subscribes one or more email addresses, sourced from an env var (`FLEX_ALERT_EMAILS`, comma-separated) with `hello@flexiness.com` as the fallback so the alarm is wired the moment this lands.
3. References the Amplify Hosting SSR Lambda's log group by name. The exact name is generated by Amplify and not knowable from inside the CDK app, so it's a required env var — `FLEX_AMPLIFY_SSR_LOG_GROUP_NAME`. Discovery instructions are in §"One-time discovery step" below. Without this value the stack should *fail loudly* at synth, not silently skip the alarm.
4. Adds a `MetricFilter` on that log group: pattern `"ERR_MODULE_NOT_FOUND"` (CloudWatch Logs filter pattern, double-quoted to match the literal substring anywhere in a log line — no field selectors needed since SSR Lambda logs are unstructured). Emits a custom metric `FlexGateway/SSR/ModuleNotFoundCount`, value 1 per match.
5. Adds an `Alarm` on that metric: `≥ 1` over a single `60s` period, `treatMissingData: notBreaching`, action → SNS topic. Threshold of 1 because this error is **never** normal — even a single occurrence means a deployment is broken.
6. Uncomments and applies the existing `/apelasource/gateway/errors` log group block (`apps/gateway/amplify/backend.ts:49-63`) — orthogonal cleanup; same stack as the new alarm so it lives in one place. Retention `ONE_MONTH`, `RemovalPolicy.RETAIN` as already drafted.

The whole thing is one new stack and roughly 50 lines of additional code.

## One-time discovery step (manual, by the user)

The Amplify Hosting SSR Lambda log group name is generated and not exposed in the Gen 2 backend stack. To find it, after the next production deploy:

```bash
aws --region eu-west-3 logs describe-log-groups \
  --log-group-name-prefix '/aws/lambda/amplify-' \
  --query 'logGroups[].logGroupName' --output text
```

Pick the one matching the production app/branch (typical pattern: `/aws/lambda/amplify-<app-id>-<branch>-<random>`), paste it into `FLEX_AMPLIFY_SSR_LOG_GROUP_NAME=...` in `env/public/.env.production`, redeploy. The name is stable for the lifetime of the Amplify Hosting branch; only changes if the branch is destroyed and recreated.

If preferred we can flip the order and *first* set up the SNS topic + email subscription and *then* circle back for the log group name, but the alarm is the load-bearing piece — without the log group name it isn't useful.

## Sketch (illustrative — final code in implementation)

```ts
// apps/gateway/amplify/backend.ts (additions)
import { Topic } from 'aws-cdk-lib/aws-sns';
import { EmailSubscription } from 'aws-cdk-lib/aws-sns-subscriptions';
import { Alarm, ComparisonOperator, TreatMissingData } from 'aws-cdk-lib/aws-cloudwatch';
import { SnsAction } from 'aws-cdk-lib/aws-cloudwatch-actions';
import { LogGroup, MetricFilter, FilterPattern } from 'aws-cdk-lib/aws-logs';
import { Duration } from 'aws-cdk-lib';

const ssrLogGroupName = process.env.FLEX_AMPLIFY_SSR_LOG_GROUP_NAME;
if (!ssrLogGroupName) {
  throw new Error(
    'FLEX_AMPLIFY_SSR_LOG_GROUP_NAME is required for the alerting stack. ' +
    'See apps/gateway/amplify/backend.ts comment + docs/plans/cloudwatch-err-module-not-found-alarm.md'
  );
}
const alertEmails = (process.env.FLEX_ALERT_EMAILS ?? 'hello@flexiness.com')
  .split(',').map(s => s.trim()).filter(Boolean);

const alertingStack = backend.createStack('flex-gateway-alerting');

const ssrLogGroup = LogGroup.fromLogGroupName(
  alertingStack, 'AmplifySsrLogGroup', ssrLogGroupName
);

const alertsTopic = new Topic(alertingStack, 'GatewayAlertsTopic', {
  topicName: 'flex-gateway-alerts',
  displayName: 'Flex Gateway production alerts',
});
for (const email of alertEmails) {
  alertsTopic.addSubscription(new EmailSubscription(email));
}

const moduleNotFoundMetric = new MetricFilter(alertingStack, 'ErrModuleNotFoundFilter', {
  logGroup: ssrLogGroup,
  metricNamespace: 'FlexGateway/SSR',
  metricName: 'ModuleNotFoundCount',
  filterPattern: FilterPattern.literal('"ERR_MODULE_NOT_FOUND"'),
  metricValue: '1',
}).metric({ statistic: 'Sum', period: Duration.minutes(1) });

new Alarm(alertingStack, 'ErrModuleNotFoundAlarm', {
  alarmName: 'flex-gateway-ssr-err-module-not-found',
  metric: moduleNotFoundMetric,
  threshold: 1,
  evaluationPeriods: 1,
  comparisonOperator: ComparisonOperator.GREATER_THAN_OR_EQUAL_TO_THRESHOLD,
  treatMissingData: TreatMissingData.NOT_BREACHING,
  alarmDescription:
    'SSR Lambda emitted ERR_MODULE_NOT_FOUND — a `serverExternalPackages` ' +
    'entry is not present in the Lambda runtime. See docs/plans/cloudwatch-err-module-not-found-alarm.md.',
}).addAlarmAction(new SnsAction(alertsTopic));
```

And uncomment (`apps/gateway/amplify/backend.ts:49-63`) the existing `/apelasource/gateway/errors` log group block, moving it into the same `alertingStack` so we have one home for observability resources.

## Verification

End-to-end, in order:

1. **Synth** — `cd apps/gateway && pnpm ampx pipeline-deploy --branch <test-branch>` *(or `pnpm ampx sandbox --once` locally first)*. Confirm the new stack synthesizes without errors. If `FLEX_AMPLIFY_SSR_LOG_GROUP_NAME` is unset, synth must fail with the explicit error message — that's the contract.

2. **Subscription confirmation** — every email in `FLEX_ALERT_EMAILS` receives an AWS confirmation email; click "Confirm subscription". Alarm will not deliver until subscriptions are confirmed.

3. **Force the alarm** — easiest way:
   ```bash
   aws --region eu-west-3 logs put-log-events \
     --log-group-name "<FLEX_AMPLIFY_SSR_LOG_GROUP_NAME value>" \
     --log-stream-name "$(date +%Y-%m-%d)-alarm-test" \
     --log-events "timestamp=$(date +%s)000,message='ERR_MODULE_NOT_FOUND test - safe to ignore'"
   ```
   You may need to `create-log-stream` first. Within ~60s the metric ticks and within ~1–2min the alarm state goes `ALARM` and SNS emails fire. (CloudWatch's exact firing latency is 1–5 min for sum-based metrics.)

4. **Reset** — alarm returns to `OK` once the period rolls over with no further matches. No cleanup needed for the test log message (retention will handle it).

5. **Real-traffic validation** — the next time a `serverExternalPackages` entry goes missing (e.g. someone removes `'posthog-node'` from `next.config.mjs` and deploys, or a new external is added without updating the trace), one canary request hitting the SSR Lambda is enough to fire the alarm. Validates we never repeat the silent-500 incident.

## Risk

Low:
- Net new resources only; nothing existing changes behavior (the commented `/apelasource/gateway/errors` block was inactive anyway).
- The CDK stack is gated by `FLEX_AMPLIFY_SSR_LOG_GROUP_NAME` — wrong/missing value fails synth loudly rather than producing a silently broken alarm.
- `treatMissingData: NOT_BREACHING` prevents flapping when no logs are arriving.
- Email-only SNS subscription is non-destructive; can layer Slack/PagerDuty on the same topic later.

## Open question

- **Should additional patterns be alarmed?** Candidates worth a second metric filter on the same log group (separate alarms, same SNS topic): `"UnhandledPromiseRejection"`, `"Task timed out after"` (Lambda timeout), `"INIT_REPORT"` Lambda init failures. Not blocking for this plan; expansion is mechanical once the first one ships.
